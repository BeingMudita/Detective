00

How to read this

One idea holds the whole project together.

Every decision below serves a single architectural thesis, which is also your strongest viva talking point:

The thesis

The game is a data-driven engine, not a hard-coded story. A case is structured data — a graph of entities, evidence, relationships, timeline events and simulated OSINT records with an authored solution rubric. The React client is a generic "player" that can render any valid case; the FastAPI backend evaluates any submission against its rubric. Adding Case #002…#100 means writing data and running a seed script — zero application-code changes. This is what separates the project from a CRUD college app.

The document delivers all 14 items you asked for, in order. Two conventions:

  • MVP ships in the first playable slice · LATER is designed now, built after MVP · STRETCH is optional depth if time allows.
  • Diagrams render on "pinned paper" cards so they stay legible in both light and dark. Green callouts are recommendations; red are risks / things to cut.

I've deliberately made the ambitious spec feasible for one student in a final year: the full vision is preserved as a roadmap, but the MVP is a thin, demonstrable vertical slice. Where you invited trade-off comparisons, I give a recommendation rather than a survey. The current build status and the month-by-month plan are in §15 at the end.

01

Product architecture

Five bounded contexts, one engine.

The product decomposes into five cooperating contexts. Keeping them separate is what makes the system data-driven and testable.

A Authoring

How a case is created and validated — as JSON (MVP) or via the visual admin editor (later). Output: a validated case graph + solution rubric.

B Case Store

The normalized, immutable source of truth for cases in Postgres. Cases are versioned; a live investigation always references a fixed case version.

C Investigation Runtime

Per-player state: what's been discovered, collected, connected, hypothesised. "Fog of war" over the case graph. The action log is the ground truth.

D Evaluation

Deterministic scoring of a submission against the rubric across six dimensions. Pure function of (case, investigation state, submission).

E Learning & Meta

Detective Academy, Watson mentor, gamification (XP/ranks/achievements), analytics. Wraps the core loop with pedagogy and progression.

◆ Cross-cutting

Identity & RBAC, action logging / integrity, notifications, and the design system — used by every context.

Why this shape

Authoring is separated from Runtime so a professor can see cases are content, not code. Evaluation is a pure module so scoring is unit-testable and explainable in a viva ("here is exactly why the player scored 86"). The Case Store being immutable/versioned means analytics across many players stay comparable.

Fig 4.1 — Core ER model (subset). Full attribute lists in docs/database.md.

Design decisions & reasoning

  • UUID primary keys — investigation resources are user-owned; opaque IDs remove enumeration/IDOR surface and keep seed data portable.
  • Case versioning — an investigation points at a case_version, never a mutable case. Editing a case creates a new version, so historical scores and analytics stay reproducible.
  • Graph-in-SQL — case_entities + relationships (adjacency list) model the graph. Postgres handles the depth we need (recursive CTEs for pivots); a dedicated graph DB is unjustified complexity for a FYP — see §14.
  • Hybrid JSONB — stable relational columns for anything queried/indexed (type, reliability, difficulty, ownership); flexible attributes/payload JSONB for entity- and action-specific fields. Avoids EAV sprawl while keeping the schema open.
  • Append-only investigation_actions — the single source of truth for scoring, analytics and integrity. Player-facing state tables (discovered_nodes, collected_evidence) are projections that can be rebuilt from the log.

Indexes & constraints (highlights)

  • Unique: users.email, cases.code, (case_id, version), (investigation_id, node_id) on discovered/collected tables.
  • Composite index (investigation_id, at) on actions for replay; (case_version_id) on all case-child tables; GIN on JSONB attribute fields used in filters.
  • FKs with ON DELETE CASCADE from case_versions to children; RESTRICT from investigations to case_versions (never orphan a played case). CHECK constraints on enums (role, reliability, status, difficulty ∈ 1–5).

Versioned REST · Pydantic-validated · OpenAPI auto-documented.

Key design point — the lookup endpoint is the game

POST /lookup takes a tool + query, matches it against the case's osint_records, and returns only what that query legitimately reveals — appending to the player's discovered set server-side. The client never receives hidden nodes. This one endpoint enforces fog-of-war, drives discovery scoring, and keeps the solution un-leakable.

06

Investigation engine

Fog-of-war over a case graph, with the action log as ground truth.

The engine is the heart of the product. It has four responsibilities: reveal (what a lookup discovers), record (append the action), project (rebuild player-visible state), and evaluate (score a submission). Crucially, the server owns the full case graph; the client only ever holds the discovered subgraph.

Fig 6.1 — Discovery loop. Every arrow back to the player passes through the reveal gate.

Reveal rules (the pivot mechanic)

Each osint_record declares a trigger (e.g. "searching username nightowl_42") and a set of reveals (entity ids, edge ids, evidence ids). Pivoting from a discovered entity via a known relationship is also a trigger. This means the player genuinely correlates: the email is only found because the same username surfaced in two independent simulated sources.

Deterministic evaluation — six dimensions

Scoring is a pure, rule-based function — reproducible, explainable, unit-testable. No LLM decides the score (an LLM may later phrase the post-mortem). Each dimension compares the player's state/log to the rubric:

Evidence Collection/25
Evidence Relevance/20
Timeline Accuracy/20
Relationship Discovery/15
Hypothesis Quality/20
Critical Reasoning/15

Critical Reasoning is the pedagogically important one: the player is rewarded for rejecting red-herring evidence and penalised for citing it as support — the game rewards reasoning, not clue-hoarding. Hints and wrong pivots are recorded and apply transparent score modifiers.

Recommendation

Keep the core scorer 100% deterministic. It is defensible in a viva ("show me why I lost 5 points" → exact rule), trivially testable, and works offline. Reserve the LLM strictly for explaining and hinting, never for grading.

Contract discipline

The importer rejects a case whose solution_rubric references ids that don't exist, whose graph is disconnected from the initial entities, or whose canonical timeline is unorderable. Bad content fails at author-time, never at play-time.

08

Watson — AI mentor & RAG

A mentor that cannot spoil the case, by construction.

Watson is a scoped, tool-calling assistant — not a chatbot with database access. Its cardinal rule: it may only reason over what the player has already discovered, plus the authored hint ladder. It never sees hidden nodes or the solution rubric.

flowchart TB
  Q["Player question /
hint request"] --> G["Guardrail layer
· intent classify
· sanitize input"]
  G --> LLM["Claude API
system prompt: mentor,
never reveal solution"]
  LLM -->|"tool call"| T1["get_discovered_entities"]
  LLM -->|"tool call"| T2["get_collected_evidence"]
  LLM -->|"tool call"| T3["get_timeline_state"]
  LLM -->|"tool call"| T4["get_next_hint(level)"]
  T1 & T2 & T3 & T4 --> SCOPE[("Scoped view:
discovered subset only")]
  SCOPE --> LLM
  LLM --> A["Grounded reply /
graduated hint"]
  A -. "hint used" .-> LOG["log action →
score modifier"]
Fig 8.1 — Retrieval is constrained to the discovered subset; the hint ladder is authored, not generated.

Why this design

  • No spoilers by construction — the tools physically cannot return undiscovered data, so even a jailbreak prompt yields nothing hidden. Safety is architectural, not prompt-dependent.
  • Authored hint ladders — hint content is written per-case (§7). The LLM only chooses which level is appropriate and phrases it conversationally; each hint used is logged and costs score. This makes hinting deterministic in effect and fair to grade.
  • Grounding > hallucination — because Watson answers from retrieved case facts, it explains "what a DNS MX record means here" rather than inventing. Great teaching, low risk.
  • Graceful degradation — if the API key is absent (offline demo, no budget), Watson falls back to the rule-based hint ladder directly. The MVP is fully playable with zero LLM calls.
Recommendation — provider

Use the Claude API (e.g. a Sonnet-class model) for Watson: first-class tool-calling maps cleanly onto the scoped-retrieval design, and you're already in the Claude ecosystem. Keep the interface behind a thin LLMProvider port so it's swappable and mockable in tests.

Non-negotiable safety posture

The application never queries a real person, domain, IP, or social account. All targets are fictional or reserved examples (*.example, RFC-5737 doc IP ranges). No scraping, no credential attacks, no unauthorized scanning, no arbitrary command execution from player input. This is stated in-app and in the README — it is central to the project's ethics, not a footnote.

Three trade-offs, decided

Graph storage — Postgres, not Neo4j

A dedicated graph DB looks impressive but adds an operational dependency, a second query language, and sync complexity for a graph that is small and bounded per case. Postgres adjacency lists + recursive CTEs handle every pivot we need. Recommend relational; mention Neo4j in the report as a scaling option.

Background jobs — FastAPI BackgroundTasks for MVP, Celery later

Celery + a broker + a worker is real infra to babysit. Nothing in the MVP needs distributed async — scoring is synchronous and fast. Start with BackgroundTasks; introduce Celery only if/when analytics aggregation or bulk case imports justify it (and cite that as a considered evolution).

Scoring — deterministic engine, not LLM-as-judge

An LLM grader is non-reproducible, hard to defend, and costs money per submission. A pure rule engine is testable, explainable to an examiner line-by-line, and free. Deterministic core; LLM only for optional qualitative phrasing of the post-mortem.
